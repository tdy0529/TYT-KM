# TYT-KM：用 LLM 與 Obsidian 建立可長期累積的研究知識庫

本教學使用 **OpenAI Codex 桌面版** 與 **Obsidian**；Codex 模型選 **GPT-5.6 Sol**，推理程度（Reasoning effort）選 **Medium**。[模型說明](https://developers.openai.com/api/docs/models/gpt-5.6-sol)

TYT-KM 把來源、來源解讀、可重用知識與專案工作分開保存，再用可追溯的連結把它們接起來。你可以先理解一篇文章，決定是否保存，逐步形成自己的概念與方法頁，並在下一個研究專案繼續使用。

Obsidian 是你的操作介面；Codex 依系統規則搜尋、整理與維護。成果保存在 Markdown 檔案中。

適用對象：不同領域的研究生。入門不要求寫程式、使用終端機或先理解 Git；你需要能找到資料夾、閱讀文字，並願意核對引用。本教學的目標是讓你能獨立完成「材料 → 證據 → 知識 → 專案 → 再利用」的循環。

## 閱讀路線

先完成第 1 章架設，再讀第 2 章了解筆記分工與對話方式。第 3 章集中實作練習；日後維護與問題排查見第 4、5 章。

## 1. 架設

### 1.1 建立練習庫

1. 在 GitHub 儲存庫選 **Code → Download ZIP**，下載並解壓縮。
2. 將裡面的 `vault` 資料夾複製到自己的工作位置，改名為 `TYT-KM-Practice`。
3. 保留原交付包，日後可再用它建立正式研究庫。

### 1.2 用 Obsidian 開啟

1. 安裝並開啟 [Obsidian](https://obsidian.md/)。
2. 選 **Open folder as vault**，開啟剛建立的 `TYT-KM-Practice`。
3. 打開 `20_Knowledge/Home.md`，從首頁開始瀏覽。

練習庫已附基本設定，開啟後即可使用。[開啟資料夾說明](https://help.obsidian.md/manage-vaults)

### 1.3 用 Codex 開始工作

1. 安裝 [OpenAI Codex 桌面版](https://developers.openai.com/codex/app/)並登入。
2. 在 Codex 加入本機資料夾 `TYT-KM-Practice` 作為專案。
3. 在該專案開啟任務，使用 **Local（本機）模式**，直接在這份資料夾工作。
4. 模型選 **GPT-5.6 Sol**，推理程度選 **Medium**。
5. 前往第 3 章，附上文章並開始練習。

Codex 與 Obsidian 使用同一份 `TYT-KM-Practice`。Codex 會讀取其中的 `AGENTS.md` 作為專案指引。[指引載入說明](https://developers.openai.com/codex/guides/agents-md)

## 2. 系統如何運作

### 2.1 五個區域與四種常混淆的內容

| 區域 | 放什麼 | 不應把它當成什麼 |
|---|---|---|
| `00_Inbox` | 未判定連結、附件、想法 | 已確認的證據 |
| `10_Sources` | 已登記原件、可重現快照 | 可任意改寫的摘要 |
| `20_Knowledge` | Source Notes、知識頁、Maps、Index | 所有聊天的堆積處 |
| `30_Projects` | 持續目標、Context、Worklog、Decision、Output | 普遍成立的研究結論 |
| `90_System` | 規則、模板、系統維護紀錄 | 學科資料的分類區 |

以論文題目 **「線上討論如何影響研究生的批判思考」** 為例，以下只是說明資料角色，沒有預設研究結果：

| 內容 | 在這個論文題目中的例子 | 角色 |
|---|---|---|
| **原件（Raw Source）** | 你閱讀的一篇相關期刊論文 PDF | 保存作者原始文字、方法與圖表，作為核對依據；不把自己的摘要寫進原件。 |
| **Source Note** | 這篇期刊論文的閱讀筆記 | 解讀單一來源：研究問題、樣本、方法、結果、限制、重要主張所在頁碼，以及你釐清的術語與問題。回答「這篇論文說了什麼、依據是什麼」。 |
| **Knowledge Note** | 「批判思考有哪些測量方式，各自適用什麼情境？」 | 保存可重用的核心知識點，綜合相關來源與推理，保留適用條件及衝突。回答一個能持續更新的問題，日後其他研究也能使用。 |
| **Project Context** | 「線上討論與批判思考論文 — Context」 | 保存你這篇論文的目標、完成條件、研究限制、目前進度、未決問題與下一步，連到需要的知識和工作成果。它是繼續研究的入口。 |

原件與 Source Note 是一組「證據與解讀」；Knowledge Note 可引用多份 Source Note 建立通用理解；Project Context 連結這些理解，交代它們在你目前論文中的用途。

專案的詳細成果另有三種角色：**Worklog** 記重要推理與進展，例如比較兩種研究設計的理由；**Decision** 記你已選定的設計及取捨；**Output** 保存實際交付物，例如研究計畫草稿或文獻比較表。Context 連到這些內容，不把全部細節重抄一遍。

### 2.2 用意圖選流程

只要先確認這次的目標、手上的材料，以及是否需要寫入檔案，就能選對流程。

| 你想做的事 | 系統流程 | 常見結果 |
|---|---|---|
| 先放著，判斷去哪裡 | Capture／Triage | Inbox 候選與下一步 |
| 看懂尚未保存進系統的文章、判斷值不值得讀 | Assess | 理解、評估、讀取範圍；可以不寫檔 |
| 保存可引用來源與閱讀成果 | Register／Ingest | 原件或 URL、Source Note、Index 與日誌 |
| 更新概念、方法、比較或綜合 | Integrate | 更新既有 Wiki，必要時才建新頁 |
| 問答庫內已知內容、判斷過程產出是否值得存 | Query／Persist | 有依據的回答；保存需交給正確流程 |
| 持續做一個研究或產出 | Project | 可交接的 Context 及必要成果 |
| 找錯誤或調整結構 | Lint／Refactor | 問題清單、允許範圍內修復或待確認方案 |

正式規則依序從 `AGENTS.md`、`90_System/Router Contract.md`、`90_System/Workflows.md` 進入。此教學是操作導覽；正式契約才定義權限與完成條件。

### 2.3 證據連結與知識導航

知識頁中的重要主張會連到 Source Note 的對應主張，再由其中的頁碼、段落、圖表或時間位置回到原件。這條連結讓你能核對解讀，並在來源更新時找出受影響的筆記。

Wikilink 是筆記之間的內部連結，可以指向整頁、章節或某個主張。連結旁的文字說明關係，例如「支持這項解釋」「限制適用範圍」或「使用這個方法」。

**Knowledge Index** 用每頁一行摘要協助搜尋；**Map** 依一個問題安排閱讀順序與關係；**Catalog** 依筆記欄位呈現可篩選的清單。

主題 Map 在至少三篇筆記已有實質關係時建立。Backlinks 顯示哪些筆記引用目前頁面，Graph 則把連結關係畫成圖；兩者方便導航，但不判定證據是否可靠。

### 2.4 筆記狀態與人工判斷

筆記狀態描述處理或審閱進度。Source Note 的 `partial` 表示只處理部分材料，`processed` 表示宣稱的範圍已完成擷取。Knowledge Note 的 `draft` 是草稿，`needs-review` 是需要人工判斷，`reviewed` 是已在明確範圍內審閱，`contested` 是保留尚未解決的可信衝突。

Codex 負責整理依據與指出限制；你負責核對關鍵解讀、判斷研究意義及接受重要選擇。來源主張、Codex 推論與你的判斷會分開標示。Decision 只有經你明確接受才標為 `accepted`。已完成擷取或審閱，不等於結論可以套用到所有情境。

### 2.5 討論成果的保存

對話先用來理解、追問與推進工作。要求保存後，系統會留下有未來價值的成果及必要理由，按內容角色寫入既有筆記或建立必要頁面。

**圍繞一篇文章的討論**，其術語釐清、推導、條件、誤讀修正及文章本身的未解問題，寫入這篇文章的 Source Note。可跨文章或跨研究使用的理解，再由 Integrate 整理到 Knowledge Note。

**圍繞專案的討論**，最新進度、阻礙與下一步，會寫入 Context；會影響後續工作的推理、排除方案及修正理由寫入 Worklog；重要專案選擇寫入 Decision；報告或比較表等交付內容寫入 Output。專案頁連到來源證據，主要記錄證據如何影響這個專案。

**學習過程**，保存的是理解如何改變及為何改變。與文章有關的修正留在 Source Note；持續學習的目標、卡點與進度留在學習專案。反覆重述、已無用途的探索與整段聊天不預設保存。精選問答可以作為筆記的表達方式，但仍需保留來源與角色。

同一次討論可以更新多種筆記，系統會回報實際檔案與未保存項目。System Log 記錄需要留痕的操作事件，不承載問答全文。

### 2.6 對話階段與換視窗的時機

這裡的「對話視窗」指 Codex 的一個任務。它承接當下的問題、材料與來回討論；筆記庫則保存下次仍要使用的成果。系統的工作階段以一個目標的完成或暫停為界，不以開關視窗為界。

**繼續同一個視窗**：正在理解同一篇文章、追問同一個問題、修正剛才的解釋，或處理同一個專案目標時，沿用原對話。從理解到保存來源、再到整理知識，也可以在同一視窗接續；不需要每換一個流程就開新視窗。隔天回來繼續同一件事，也不必只因為換了一天就開新視窗。

**另開新視窗**：開始不相關的主題或另一個專案，或原對話已混入多個目標、過時假設與無關內容，導致難以維持焦點時，先保存有價值的成果，再開新任務。沒有固定輪數或文章篇數的換視窗門檻。

**換視窗前**：完成來源筆記或知識筆記的必要更新；有專案時整理目前狀態、未解問題與下一步。先確認檔案已寫入，再結束對話。只看懂而沒有保存需要的內容，可以直接結束。

**換視窗後**：仍在同一個 Codex 資料夾專案中開啟 Local 任務，指出要接續的 Source Note、Knowledge Note 或 Project Context，以及這次要完成的事。Codex 依檔案恢復工作，不把未保存的舊問答當作可靠交接。新對話所需材料尚未存入庫時，重新提供必要材料。

兩個視窗可以處理不同工作，但避免同時修改同一篇筆記或同一份專案進度。接續操作的實際 prompt 見練習 C6。

## 3. 實作練習

準備一篇想理解的文章，提供全文、檔案或可開啟的連結；有關鍵圖表時一併提供。各題只要貼上「你可以這樣說」的文字，再把方括號 `[ ]` 裡的內容換成自己的。

- **A：先保存和處理文章，再討論與累積知識。** 從 A1 開始。
- **B：先延伸討論，最後一起保存成果。** 做完 A1 後接 B2；B1 說明起點。
- **C：帶著持續目標做研究或學習。** 準備目標、交付物、時間與限制，從 C1 開始。
- **D：查詢、比較、導航與維護。** 依當下需求選題。

### 路線 A｜從「看懂一篇文章」到「累積可重用知識」

#### A1. 我只是想看懂文章

**先準備**：一篇尚未保存的文章，附上全文、檔案或可讀連結。

**你可以這樣說**：

```text
我要理解這篇文章在幹嘛，請幫我整理重點。
```

**系統應如何回應**：說清楚文章的問題、做法、主要主張、依據與限制，交代實際讀了哪些內容，簡短評估值得注意或繼續閱讀之處。若無法取得全文，應說明缺口。此時可以只回答，不建立筆記。

**操作提醒示意**：「目前先協助理解，尚未保存。這篇與你關心的問題有關；如果要留下，可保存原文及閱讀筆記。」只有材料確有用途時才提出這項建議。

**這一步對應什麼**：Assess。它處理尚未登記材料的理解與評估；不是一收到文章就完整入庫。

**自己檢查**：回原文核對一項重點；分清作者原話、助手解釋與還不知道的事。

#### A2. 這篇值得留，幫我保存

**先準備**：A1 的文章與回應。若原文取不到，先補上材料，或接受系統明示只能記錄可存取範圍。

**你可以這樣說**：

```text
這篇我想留下來，請幫我保存文章和閱讀筆記，之後可以回頭查。
```

**系統應如何回應**：說明保存位置，保存原件或可追溯來源，建立來源筆記，收錄先前討論中有價值的文章理解，保留讀取範圍、引用位置與限制，完成必要索引及驗證。

**操作提醒示意**：「文章與閱讀筆記已保存，這裡是連結。先打開閱讀筆記，看看重點是否符合原文；有疑問可直接指出段落。」

**這一步對應什麼**：Register／Ingest。原件進 `10_Sources`；單一來源的解讀形成 `20_Knowledge/Source Notes` 下的 Source Note。這一步未必需要另建通用知識頁。

**自己檢查**：實際開啟來源筆記，沿一個重要主張找到原文位置；不要只看助手的「已完成」。

#### A3. 我讀了筆記，還有問題

**先準備**：打開 A2 產生的 Source Note，選一個不懂的概念、推論或段落。附上筆記連結或摘錄，讓助手知道你指哪裡。

**你可以這樣說**：

```text
我讀了這份筆記，還是不懂「[概念或段落]」。可以換個方式解釋嗎？
```

**系統應如何回應**：從已保存的理解與來源回答，必要時回原文核對。例子與推導要標示角色，不應假裝都是作者說的。若只是換句話說，留在對話即可。

**操作提醒示意**：「這次補出了筆記缺少的適用條件，值得補回原筆記。」若只是重述，則簡短說明沒有新增保存價值，不必提議另建頁。

想保留剛釐清的內容時，再說：

```text
請把剛釐清的重點補回那份筆記。
```

**這一步對應什麼**：先是 Query／Persist；需要補充文章特定的條件、解讀或更正時，交給 Register／Ingest 更新既有 Source Note。若答案仍需要另一份未登記材料，系統應另走 Assess。

**自己檢查**：原筆記有合理更新，沒有多出一篇同義摘要；你自己的推論沒有被寫成作者的結論。

#### A4. 這個理解以後還會用到

**先準備**：從前面討論挑出一個不只是在複述文章、而且之後還想持續查用的概念、方法或比較問題。已有相關閱讀筆記就一併指出。

**你可以這樣說**：

```text
關於「[問題]」，請把我們弄懂的內容整理成以後可以持續補充的筆記，
並和我已有的相關內容連起來。
```

**系統應如何回應**：先找既有同義內容，優先更新；區分來源支持的理解、綜合推論與適用限制。依據足夠、問題獨立才建新知識頁；若只是重述來源或證據不足，說明保留現狀或延後的理由。

**操作提醒示意**：「這部分可以整理成回答『[問題]』的知識筆記，證據仍連回文章。現有理解只來自這份來源，適用範圍需要保留。」

**這一步對應什麼**：Integrate，把來源理解或討論成果編譯進 Knowledge Notes，並更新索引及必要關聯。單一來源不是禁止條件，但不能把它包裝成多來源共識。

**自己檢查**：知識頁回答一個可持續更新的問題，能連回 Source Note；「Source Note → Knowledge Note」的差別是用途與內容角色，不只是換資料夾或標題。

### 路線 B｜先持續討論，再保存內容與學習成果

#### B1. 從文章理解開始

沿用 A1 的文章與回應，在保存文章前接著做 B2。已完成 A2 時，另選一篇尚未保存的文章，再依 A1 開始。

#### B2. 從文章延伸到我真正卡住的問題

**先準備**：一個你真的不懂的地方。每次選一個問題，依回應再追問；不用把所有提示一次貼完。

**你可以這樣說**：

```text
作者為什麼能從「[依據]」得到「[結論]」？
```

接著可用自己的理解確認：

```text
我的理解是「[你的說法]」，這樣對嗎？如果換成「[另一情況]」還成立嗎？
```

**系統應如何回應**：回到文章定位依據，幫你檢查推理。文章沒談的情境，要區分推論與未知；需要補充材料時說明缺什麼。仍依賴未登記文章的追問，不能因為聊了很多輪就假設已入庫。

**操作提醒示意**：「我們釐清了這個條件，也修正了原先的理解；目前仍只在對話中。若最後要保存，可以一起保留這些修正及尚未解決的問題。」

**這一步對應什麼**：持續 Assess；只有既有 Wiki 本身已足以回答的部分，才另走 Query。對話長度不決定是否建立 Project。

**自己檢查**：挑出一個自己先前誤解、現在能說清楚的地方，指出是什麼依據改變了理解。

#### B3. 把這次學到的內容留下來

**先準備**：同一工作鏈中的文章與討論。若換了工具或對話，補上必要討論摘要，助手不能假裝看過無法取得的歷史。

**你可以這樣說**：

```text
請把這篇文章和我們這次討論學到的重點保存下來，
包括修正過的理解和還沒弄懂的問題，讓我下次能接著看。
```

**系統應如何回應**：先辨認有未來價值的成果，再按角色保存：文章特定的主張、條件與解讀回到 Source Note；可重用理解交給 Knowledge；使用者判斷保留角色。已被推翻的想法，只有其修正理由對未來有用時才留下，不能和現行結論並列成兩份真相。

**操作提醒示意**：「我會保存文章與閱讀成果，把可重用的理解另行整理，保留必要的誤解修正及待解問題；不需要保存整段聊天。」完成後需明列實際保存位置，以及延後或未保存的項目與原因。

**這一步對應什麼**：Assess handoff → Register／Ingest；有可重用且已授權的成果時再 Integrate。這次自然語言已授權文章與學習成果保存，常規草稿不需再重複確認。

**自己檢查**：不是只有第一輪摘要被保存；後續重要釐清有去處。若仍無法重用，系統說明缺口即可，不必硬建知識頁。

#### B4. 我想持續學，不只是留下一次閱讀成果

**先準備**：想持續學的主題、下次要解決的問題，以及可觀察的學習目標，例如「能比較兩種解釋」「能寫出一頁方法說明」。只有想保存這篇閱讀成果時，到 B3 就可停止。

**你可以這樣說**：

```text
我想把「[主題]」當成接下來持續學習的專案，目標是「[能做到什麼]」。
請整理目前懂了什麼、卡在哪裡，以及下次從哪裡繼續。
```

**系統應如何回應**：建立最小學習專案，保存目前狀態與下一步；對後續學習有用的推理過程才留下壓縮紀錄，並連到 B3 的閱讀成果。若目標不清，只補問會影響安排的必要資訊。

**操作提醒示意**：「已建立持續學習的入口；下次打開這份進度筆記即可接續。文章理解仍連回來源筆記，這裡保存你的學習目標與進度。」

**這一步對應什麼**：Project Context 與必要 Worklog。這才是持續保存「學習過程」的情境；不是將所有問答全文寫入 Knowledge。後續可接 C4–C7。

**自己檢查**：進度、卡點與下一步可找到；文章證據沒有被大量複製到專案紀錄。

### 路線 C｜帶著目標讀材料，逐步完成一個專案

#### C1. 我有一件要持續完成的事

**先準備**：一個真實目標、預期交付物、期限或時間範圍、已知限制，以及已有的材料。例：兩週後交一份比較報告、準備一次文獻報告、逐步釐清一個研究問題。尚未確定的資訊可直說未知。

**你可以這樣說**：

```text
我想建立一個專案，完成「[成果]」。目前有「[材料或進度]」，
希望在「[時間]」前完成，主要限制是「[限制]」。請幫我整理起點和下一步。
```

**系統應如何回應**：先確認目標與完成條件，搜尋已有理解，建立最小 Context。只有實際需要時才增添工作紀錄或交付物，不預先堆出空白文件。

**操作提醒示意**：「已整理成專案入口，包含目標、限制、目前狀態與下一步。之後可以從這裡接續。」

**這一步對應什麼**：Project。若先做 B4，已有同一目標的 Context，就沿用它，不另建專案。

**自己檢查**：另一個人只讀入口就知道要完成什麼、目前在哪裡、接著讀什麼。

#### C2. 這篇文章對我的目標有用嗎

**先準備**：C1 的專案與一份相關材料。可拿之前只一般讀過的文章，練習改用專案目標重新評估。

**你可以這樣說**：

```text
這篇文章對我的「[專案名稱或目標]」有什麼幫助？我應該先看哪裡？
```

**系統應如何回應**：先讀專案狀態，再說明材料支持哪個問題、改變哪些限制、缺哪些證據，建議最小閱讀範圍。先前讀過文章也不能只搬回一般摘要。

**操作提醒示意**：「這份材料能幫你比較其中一項條件；目前先作專案參考，還未保存成可穩定引用的來源。」只在材料尚未登記時這樣提醒。

**這一步對應什麼**：未登記材料走 project-relative Assess；有影響未來工作的成果再由 Project 保存，記清出處、讀取範圍與未登記狀態。若材料已登記，則沿既有來源／知識查用，不重複登記。

**自己檢查**：回答有連到專案的具體需求，且「已寫進專案紀錄」不會被誤認為「已正式登記來源」。

#### C3. 我要保留這篇作為依據

**先準備**：C2 指出的具體用途。若 C2 已因既有授權完成來源保存，直接開啟核對即可，不必重做。

**你可以這樣說**：

```text
這篇會用來支持「[具體論點或選擇]」，請保存文章和閱讀重點，
並記下它對這個專案的影響。
```

**系統應如何回應**：保存來源與解讀後，再把對專案的影響接回 Context 或必要 Worklog；沿用既有 source ID，避免重複原件與來源筆記。

**這一步對應什麼**：Register／Ingest → Project handoff。來源保存「文章說什麼」，專案保存「這對我們的工作意味著什麼」。

**自己檢查**：專案能連到可回查的依據，原本評估中會影響後續工作的結論沒有遺失。

#### C4. 討論選擇，留下有用的過程

**先準備**：專案中兩個確實可行的選項、你在意的比較條件。若沒有選擇題，可用一個尚未解決、會影響下一步的研究問題替代。

**你可以這樣說**：

```text
針對這個目標，「[選項一]」和「[選項二]」各有哪些理由和限制？
```

先討論，再於本次工作結束時說：

```text
請把今天的重要討論和進度留下來，包括排除哪些做法、原因和未解問題，
讓我下次接著做。
```

**系統應如何回應**：區分文獻證據、專案推論、偏好與建議；保留會影響後續工作的壓縮成果。助手推薦的選項不能自動變成你已接受的決定。

**操作提醒示意**：「比較理由與目前進度已保存；選項仍待你決定。」若你已明確決定，則如實記錄，不再說未決。

真有決定時再說：

```text
我決定採用「[選項]」，主要因為「[理由]」，請把這個決定記下來。
```

**這一步對應什麼**：Project discussion handoff：Context、必要 Worklog，以及達門檻的 Decision。使用者明確接受後才記 accepted；小型可逆選擇可留在 Context 或 Worklog。

**自己檢查**：能找回理由與重要修正，不需要重讀聊天；沒有把建議當成決定。

#### C5. 把累積成果做成可交付內容

**先準備**：交付對象、用途與形式，例如給同學的一頁說明、文獻比較表、方法草案。先用 Markdown 完成一次即可。

**你可以這樣說**：

```text
請根據目前成果，整理一份給「[對象]」看的「[交付物]」，用途是「[用途]」。
```

**系統應如何回應**：依專案目標產出 Output 草稿，交代所依賴的知識、來源與限制，將進度接回專案入口。

**操作提醒示意**：「草稿已放在專案交付物中；請檢查是否回答了原定問題，以及哪些部分還需要你確認。」

**這一步對應什麼**：Project Output。交付物完成不表示所有內容都成為通用知識，也不等於獲准對外發送或發布。

**自己檢查**：Output 可獨立閱讀，結論仍能追溯依據，未完成部分沒有被包裝成確定成果。

#### C6. 隔天回來，從上次接著做

**先準備**：在新對話提供系統產生的專案入口連結、路徑或可辨識專案名稱，不提供整段舊聊天。

**你可以這樣說**：

```text
我要繼續「[專案名稱]」。請先告訴我上次做到哪裡、還缺什麼，
再帶我做下一步。
```

**系統應如何回應**：從 Context 與必要閱讀路徑恢復工作，區分已完成、未決與下一步。若找到多個同名目標，應釐清而不是猜。

**這一步對應什麼**：Project 的跨工作階段 handoff。若需要新材料，再依材料狀態進入下一個流程。

**自己檢查**：未依賴原聊天仍能正確接續；「可以恢復工作」比存了多少篇紀錄更重要。

#### C7. 哪些成果值得帶到下一個專案

**先準備**：專案中形成的方法、比較框架或重要洞見，並指出可能如何在其他情境使用。

**你可以這樣說**：

```text
這次有哪些理解或方法以後還用得上？請整理保存，和我原本的相關筆記接起來。
```

**系統應如何回應**：檢查可重用性與證據，移除特定專案的偶然限制，優先更新已有知識，保留專案出處。證據不足或需要你判斷的泛化，先交代缺口與具體差異；不必強迫每個專案產生新知識。

**操作提醒示意**：「比較框架可以留作後續使用；這次選擇的特定安排仍留在專案。某項推論還缺驗證，暫不升級。」

**這一步對應什麼**：Project promotion candidates → Integrate 的 Project-origin 檢查，並把結果同步回 Context。

**自己檢查**：看得到哪些被整合、哪些延後及原因；專案決策沒有被誤寫成普遍建議。

### 路線 D｜依需要選做的延伸情境

#### D1. 現在沒空讀，先收起來

**先準備**：幾則連結、附件或零散想法，尚未決定要做什麼。

**你可以這樣說**：

```text
這些先幫我收著，簡單分一下哪些值得之後看。
```

**系統應如何回應**：收件與分流，說明候選及下一步；不把快速分流當成完整閱讀。涉及刪除時先取得同意。

**功能與驗收**：Capture／Triage。可在 Inbox 找到未決材料，與已登記來源清楚分開。

#### D2. 材料很長，我只想解決一個問題

**先準備**：尚未登記的長文章、書籍章節、含圖報告或影片，加上一個具體問題；影片需可存取內容或逐字稿，不能只憑標題。

**你可以這樣說**：

```text
這份內容很長，我現在只想弄懂「[問題]」。請帶我看最相關的部分。
```

**系統應如何回應**：先縮小範圍，必要時建立結構索引，區分已抽取、已核對、未核對與建議閱讀範圍；重要圖表需實際查看。不能把文字擷取成功當成全部讀懂。

**功能與驗收**：Assess 與閱讀範圍控制。學生能回到一個頁碼、章節或時間段核對；無法讀取或看圖時有明確限制。

#### D3. 我以前是不是已經學過這個

**先準備**：完成 A4 或 B3 後，用同義詞或自己的說法問同一問題，不再附原文。

**你可以這樣說**：

```text
根據我之前整理的內容，「[問題]」目前可以怎麼理解？
```

**系統應如何回應**：從既有知識搜尋與回答，指出證據與缺口。若庫內沒有答案就說明，不以外部新資料假裝庫內已知。

**功能與驗收**：Query／Persist、同義檢索與合理不保存。能找到既有頁；只是重述時不另建筆記。若回答真的形成新框架，系統可以說明保存價值，使用者有需要再說「這個整理有幫助，請保存」。

#### D4. 新文章的說法好像不一樣

**先準備**：一份既有來源，以及同問題的新文章、不同觀點或原文勘誤。找不到矛盾材料，可改練比較適用範圍，不必製造假衝突。

**你可以這樣說**：

```text
這篇和我之前讀的「[文章或筆記]」說法好像不同，請幫我比較。
```

理解差異後，確實想保存再說：

```text
請把新材料和這次比較的重點保存下來，更新我之前的理解。
```

**系統應如何回應**：先讀新材料，再對照既有理解；比較定義、條件、證據與版本。保存時區分新獨立研究與舊文勘誤，不改寫舊原件，保留可信衝突。若涉及 reviewed 核心結論或互斥解釋，先呈現差異供人判斷。

**功能與驗收**：Assess → Query；授權後 Register／Ingest → Integrate。比較能回到雙方依據，沒有默默抹除舊說法或把不同測量當成直接矛盾。

#### D5. 我有幾篇筆記，想知道怎麼讀才串得起來

**先準備**：至少三篇實質相關的既有 Note，及你想解決的主題問題。

**你可以這樣說**：

```text
我想把「[主題]」串起來，請替這些筆記整理一條閱讀路線並保存。
```

**系統應如何回應**：依問題安排順序，解釋每個連結的用途、關係與缺口；現有導航足夠就更新，不重建。若不足三篇相關 Note，指出不足，不硬拆頁湊數。

**功能與驗收**：Integrate 建立或更新 Map，配合 Index 的摘要導航。你也可以自行用 Obsidian 的 Catalog 找出待複核內容、用 backlinks 觀察哪些頁引用了它；這些視圖不等於證據審核。

#### D6. 筆記有重複或連結找不到

**先準備**：自己的練習庫，最好指出一處真實問題；先保留可回復副本。沒有問題時，得到「未發現需修正處」也是有效結果。

**你可以這樣說**：

```text
請幫我檢查這個筆記庫，有沒有重複、找不到的連結，或需要我確認的內容。
```

**系統應如何回應**：列出問題所在、證據、影響與建議。無歧義機械錯誤可修復並核對；合併、拆分、刪除與語意改動要先提出具體方案。

只有實際看過且同意方案後，再用自然語言指名範圍，例如：

```text
我同意把「[筆記一]」和「[筆記二]」依你剛才的方案合併，請處理。
```

**功能與驗收**：Lint／Refactor。檢查範圍、核准範圍與實際變更一致，必要連結及索引已同步。回復練習可在副本中還原一份誤改檔，確認內容能找回。

#### D7. 這個專案先停，或已經做完

**先準備**：已有 Context 的專案、目前成果，以及你真實的暫停原因或完成情況。兩個 prompt 擇一。

**你可以這樣說**：

```text
這個專案先暫停，請整理目前成果、未解問題和以後重啟需要知道的事。
```

或：

```text
這個專案已達成原定目標，請幫我整理結案內容和還值得保留的問題。
```

**系統應如何回應**：核對目標與狀態，留下恢復入口或結案成果，維護候選知識與索引，依規格做日誌及完整 lint。尚未完成的目標須揭露；暫停不等於刪除。

**功能與驗收**：Project 生命週期 → Lint。狀態符合事實，成果仍可找到；有候選不表示自動升級成通用知識。

#### D8. 使用方式反覆出問題

**先準備**：實際發生的回應或檔案位置、預期行為與觀察到的差異。不要為了練習杜撰問題。

**你可以這樣說**：

```text
我幾次遇到「[實際狀況]」，原本希望「[預期結果]」。
請幫我查一下原因，並把需要追蹤的問題記下來。
```

**系統應如何回應**：區分材料不足、單次錯誤與反覆的系統行為缺口；有必要才保存 Observation。能直接處理的局部問題依權限修正，涉及核心規則則提出差異，不自動修改。

**功能與驗收**：問題查詢與 System Observation，必要時再進入獲核准的系統調整。紀錄可指向具體案例；「記下問題」不等於「已接受規則變更」。

## 4. 長期維護

以下是建議習慣，不是強制排程。

| 時機 | 做什麼 | 何時可以停 |
|---|---|---|
| 每次讀新材料 | 先 Assess，確定用途與閱讀範圍 | 不值得保存就停在理解 |
| 每次寫入 | 核對實際變更、欄位、連結、locator、索引 | 局部 lint 與該流程 Verify 完成 |
| 工作階段結束 | 有持續專案時更新 Context，保留有未來價值的成果 | 下一人能由 Context 恢復 |
| 每週約 15–20 分鐘 | 看 Inbox、待複核與進行中專案 | 每個重要待辦有下一步，不要求清空 |
| 新證據出現 | 搜尋同義詞、舊頁與 backlinks，更新現有理解 | 下游需要同步處已處理，未知仍明示 |
| 里程碑或漂移訊號出現 | 依規格完整 lint，必要時提出 Refactor | 每項發現都有處置與核准狀態 |
| 升級系統版本前 | 備份、比較規則差異，在副本驗證 | 確認相容性才套用正式庫 |

每累積 10 篇 processed Source Note，或遇到專案里程碑、暫停、結束、核心結構改動與漂移訊號時，依 `90_System/Workflow Specs/Lint and Refactor.md` 判斷是否需要完整 lint。通過檢查不表示所有學科結論都已審核。

Git 記錄檔案版本，System Log 記錄應留存的變更理由；兩者用途不同。初學者可先用有日期的資料夾備份，再逐步學習 Git。同步不等於獨立備份，也不要把公開系統儲存庫當作私人研究的預設上傳位置。

## 5. 常見問題

| 現象 | 先檢查 | 下一步 |
|---|---|---|
| Codex 說完成，檔案卻沒變 | 任務是否在正確的本機資料夾 | 核對回報路徑並開啟檔案查看差異 |
| Obsidian 看不到剛建立的檔案 | 是否開了另一份 Vault | 比對完整路徑再繼續 |
| 連結打開空白頁 | 名稱、路徑、heading／block 是否存在 | 修正目標，不為消除錯誤建空白頁 |
| Catalog 沒列出筆記 | Bases 是否啟用、type／status／篩選條件 | 修欄位或篩選，不把 Base 當成索引替代品 |
| 找到三篇幾乎同名筆記 | aliases、既有頁與 backlinks | 先評估合併及影響，得到同意再改 |
| 摘要流暢卻不可信 | claim 是否能回到原文與條件 | 補證據或降低結論強度 |
| 文獻互相矛盾 | 是否真的測同一問題、是否為勘誤 | 區分範圍、版本與可信衝突 |
| 對話很長，下一次卻接不上 | Context 是否含最新狀態與閱讀路徑 | 保存壓縮成果，不保存整段聊天 |
| LLM 每次都讀整庫 | 是否先讀 Router、Index／Context | 指定以問題縮小範圍，揭露實際讀取量 |
